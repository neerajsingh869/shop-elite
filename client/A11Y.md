# Accessibility

Target: **WCAG 2.2 Level AA**.

Where this started: `grep -rn "aria" client/src` returned **0**. So did `role=`.
There was no focus management, no live regions, 13 `<h1>` and no `<h2>`, and several
controls that could not be reached with a keyboard at all.

## How it is checked

| Check | Command | Catches |
|---|---|---|
| Static | `pnpm lint` (`eslint-plugin-jsx-a11y`) | missing alt, handlers on non-interactive elements, labels pointing at non-inputs, bad ARIA on a role |
| Runtime | axe-core over every route **and** every open overlay | contrast, names, roles, landmark and heading structure |
| Behaviour | scripted keyboard pass | focus order, focus trap, focus restore, `inert` |
| Human | VoiceOver | whether any of it is actually usable |

The first three are automated. The last one is not optional — automated tooling
covers roughly a third of WCAG, and everything below that is about *ordering* and
*wording* is invisible to a scanner.

### Running the audit

`scripts/a11y-audit.mjs` drives a real Chrome, runs axe-core on every route **and**
every overlay while it is open, then runs a scripted keyboard pass. It is not wired into
`package.json` on purpose — it needs `playwright` and `axe-core`, which are not
dependencies of this app:

```bash
# terminal 1                       # terminal 2
pnpm --filter server dev           pnpm --filter client dev

# terminal 3
mkdir -p /tmp/a11y && cd /tmp/a11y
npm i playwright axe-core
node "<repo>/client/scripts/a11y-audit.mjs"
```

## Decisions worth explaining

### Native elements first, ARIA only where HTML runs out

Almost every fix here was deleting a `<div onClick>` and writing `<button>`. A native
button is focusable, has a role, has a name from its content, fires on Enter *and*
Space, and works with voice control and switch devices. Rebuilding that with
`role="button" tabIndex={0} onKeyDown` is four behaviours to reimplement and at least
one of them will be wrong — usually Space, which scrolls the page unless you call
`preventDefault`.

The one place HTML genuinely runs out is the modal dialog, which is why `Modal.tsx`
is the only component with real ARIA plumbing.

### The account menu is a disclosure, not a menu

`Header.tsx` uses `aria-expanded` + `aria-controls`, **not** `role="menu"`.
`role="menu"` is a promise: arrow key navigation, Home/End, typeahead, and focus
management between items. We implement none of that, and a role that lies about its
behaviour is worse than no role — a screen reader user presses Down expecting to move
through items and nothing happens.

### Search is an `aria-activedescendant` combobox

`SearchBarModal.tsx` follows the APG combobox pattern: DOM focus never leaves the text
input, and `aria-activedescendant` tells the screen reader which `role="option"` is
current. The alternative — moving real focus into the results list — fights with
typing, because every keystroke would need to hand focus back.

The consequence is that options are deliberately *not* focusable and deliberately have
no key handlers. That's why there is an `eslint-disable` on the `<li>`, with the reason
written next to it.

### `inert` on `#root`, not just `aria-modal`

All three overlays portal to `document.body`. `aria-modal="true"` asks assistive tech to
ignore everything outside the dialog, but support is uneven and it does nothing about
the tab order. Setting `inert` on `#root` removes the background from both the
accessibility tree and the tab order, which is what actually holds.

The focus trap in `Modal.tsx` is still there as well, because `inert` is not universally
supported yet.

### Focus restore is the part people forget

On close, `Modal.tsx` returns focus to whatever opened it. Without that the browser drops
focus on `<body>`, so the next Tab starts from the top of the document — a keyboard user
who opens and closes the cart loses their place on the page entirely.

### Skeletons say one thing instead of nothing

A loading grid is 24 pulsing empty divs. To a screen reader that is either silence or 24
blank list items. The bones are `aria-hidden` and a single `role="status"` announces
"Loading products…". Page-level skeletons wrap everything in `aria-hidden`, which also
swallows the nested grid skeleton's own status so nothing is announced twice.

### No "added to cart" announcement, on purpose

Adding to the cart opens the drawer, which is announced as "Your Cart, 3 items, dialog".
A second live region saying "added to cart" would talk over that. More live regions is
not more accessible.

### Contrast: the palette moved

`text-zinc-500` on `bg-zinc-950` computes to about **4.1:1**, under the 4.5:1 minimum for
body text (1.4.3). `text-zinc-600` was about **2.6:1**. Both were raised to `zinc-400`
(~7.5:1). The UI reads slightly lighter than the original design. That was a deliberate
trade — the alternative was a design that looked good on a nice monitor in a dark room
and failed for anyone with low vision or any glare.

Inline links inside paragraphs also got `underline`: colour alone is not a sufficient
distinction (1.4.1), and axe flagged it on the auth pages.

### Virtualization vs. the accessibility tree

`VirtualGrid` renders only the visible rows, so a screen reader and browser find-in-page
both see a fraction of the list. There is no way to have both virtualization and a
complete DOM. The compromise is an `sr-only` "Showing N of M products" so the real total
is at least available. It is deliberately *not* a live region, which would fire on every
scroll tick.

This is a genuine unresolved tension, not a solved problem.

### The bug axe could not see

`useScrollToTop` scrolled the page by calling `scrollIntoView()` on an empty anchor div
at the top of the page content. That is visually correct, and axe reported nothing —
the DOM order was right the whole time.

But `scrollIntoView()` also sets Chrome's **sequential focus navigation starting point**.
So on every page, the first Tab press resumed from *inside* `<main>` and skipped the skip
link and the entire header. The skip link existed, was correct, and was unreachable.

Replaced with `window.scrollTo`, which does not move that point. This is the argument for
keeping a scripted keyboard pass: a static scan of the markup would never have found it.

## Bugs found along the way

Not accessibility issues, but found while doing this and fixed:

- `tsc` had been failing since `2b61909` — `CartItem.tsx` imported the `CartItem` type
  and also declared a `CartItem` component, so the default export was ambiguous under
  `verbatimModuleSyntax`.
- `Star.tsx` built its size classes with `w-${size}`. Tailwind scans for complete class
  names, so those classes were never generated and every star rendered at the SVG
  default size.
- `CartDrawer` mapped cart items with no `key`.
- The price slider only applied on `pointerup`, so keyboard users could move it with the
  arrow keys and nothing ever happened.
- Review percentages were `NaN` for products with no reviews.
- A `console.log` left in `VirtualGrid`'s render path.
- Five 0-byte files, including `ErrorBoundary.tsx` — so the app had no error boundary
  despite the file existing.

## Known gaps

- **Tested with VoiceOver only.** NVDA and JAWS differ, particularly around
  browse-mode vs focus-mode, which affects the combobox.
- No automated a11y tests in CI. The lint rule is the only standing guard; the axe run is
  a script, not a test suite.
- Touch target sizes (2.5.8) have not been audited.
- The Razorpay payment sheet is a third-party iframe and is outside our control.
